## 1. `0x0A` 老同步：ACK 成功但零数据，到底是协议里缺了什么？

**已知**

- `0x0A/0x02 FileParameters` 正常协商：`packetSize=974, maxBlockSize=21428, timeout=15000`。
- `0x0A/0x04 RequestBlock`（`size=4096`）回 ACK `7F04 000186A0`（成功码）；
  换成 21428 / 974 / 9740 就回 `000186A1`（另一个错误码）。
- 各种组合累计试了 **29 次以上**，`0x0A/0x05` **一包都没有**。
  用绕过 dispatcher 的旁路日志（`PROBE0A05`，在分发前打点）确认：数据包根本没到手机。
- 同一台设备上 `0x2C` 全流程正常。

**对照 `0x2C` 的差异**（我读代码看到的，但不确定是否关键）

| 项 | `0x2C` 新同步 | `0x0A` 老同步 |
|---|---|---|
| 用 id 还是文件名 | `fileId`（0x0f 等） | 文件名（`sleep_data.bin`） |
| 按块请求前 | 先 `0x2C/0x01 init` 拿 `dictId`（加密字典），`0x2C/0x04` 带 `dictId` 和 `noEncrypt` | 无 dictId 概念 |
| 块大小来源 | `0x2C/0x03 FileInfo` 回 `burstSize` / `maxBlockSize` / `noEncrypt` | `0x0A/0x02` 回同类参数 |
| 结束 | `0x2C/0x06` Complete | 没实现 |

**要你给**：对着 `FileDownloadService0A.java` 和 `FileDownloadService2C.java`
逐字段列一张 diff，回答：**`0x0A/0x04` 的请求里缺哪个字段才会出现「ACK 成功但设备不发数据」？**
如果结论是「这块固件根本没实现 `0x0A` 数据通道、ACK 只是保活」，也直接说，
我就把 `0x0A` 从研究清单里划掉，不再浪费同步窗口。

## 2. 用什么姿势枚举设备的文件空间（不下载的前提下）

**已知**：`HuaweiFileDownloadManager.FileType` 里 0x00–0x1b 的 id 是从
`com.hihonor.health` 的字符串里扒出来的，**0x1c 以上未知**。我们已经知道
`0x0d`/`0x11`/`0x12`/`0x15`/`0x1a` 在枚举里是空的，说明 id 空间不是连续的。

**新发现（想请你确认可用性）**：`0x2C/0x02 FileRequestHash`

```java
// FileDownloadService2C.FileRequestHash.Request
new HuaweiTLV().put(0x01, fileId).put(0x02, (byte) 0x01);
// Response: fileId + fileHash(0x03)
```

它**只发一个 id、只回一个 hash**，不传数据。而 Gadgetbridge 现在只在
`isInitFormDevice()`（OTA/表盘那种设备主动发起的请求）里调它，
**数据文件从来不用**（`HuaweiFileDownloadManager.getFileHash()` 的调用点只有一处）。

**我打算做的实验**：对 id `0x00`–`0x40` 逐个发 `0x2C/0x02`，记录 id → hash 或错误码。

**要你给**：

1. tag `0x02 = 0x01` 这个标志位是什么？（我在代码里没找到语义，猜是「要哪种 hash」）
2. 设备对**不存在的 id** 会回什么？`0x7F` 错误码？空 hash？还是直接不回？
   我需要一个判据把「这个 id 存在但没数据」和「这个 id 不支持」分开。
3. 这个 sweep 有什么风险？（比如会不会触发固件的删除/重置语义——`0x02` 听起来像只读，
   但我想让第二双眼睛确认。）

如果这个 sweep 可行，收益是：**一次 10 秒的扫描就能拿到整台设备的文件清单**，
而不是像现在这样每次同步盲试 17 个文件、每个都下 100 KB 再丢掉。

## 4. `sleep_data.bin` 的 TruSleep 格式：怎么把文法反推到能验证

**已知**

- 105716 字节；零填充 + 记录序列；记录里 ACC（体动）tag=1 / PPG（脉搏波）tag=2。
- 我们的解码器（`decoders/decode_sleep_beats.py`）能解出**每晚约 2 万～3 万拍**，
  每拍带相对时间偏移和峰值。
- 但**没有独立数据源能验证**：数据库里的睡眠分期（`RAW_KIND` 6/7/8）粒度太粗。

**要你给**：一个**可验证**的反推方法。我的想法是拿三个约束同时卡：

1. 记录长度必须整除总长度（在跳过零填充后）；
2. 解出的拍间隔必须落在 250–2500 ms（生理上限）；
3. 同一时段的 RRI 实时流（`raw-rri_*.csv`，中位 5 拍/4 秒）与 blob 解出的 RR 序列
   **在时间轴上要对得上** —— 这条是真正的 oracle，因为它来自完全不同的通道。

请judge：这个三方约束够不够定位记录边界？如果不够，还差什么约束
（校验和？时间戳绝对值？PPG 采样率？）另外，`0x2C/0x01 init` 回来的 `dictId`
是不是这个 blob 的加密字典 —— 如果是，我们能拿到解密后的明文吗？

## 5. `NEWSYNC truSleep=true rri=true gps=true`：那个 `rri=true` 到底指什么？

**已知**：连接时日志 `NEWSYNC truSleep=true rri=true gps=true`，三个能力位全 true。
但 `rrisqi_data.bin`（id `0x10`）走 `0x2C` 拿回来**恒为 0 字节**，
所以逐拍数据只能靠实时流 `0x19/0x05`（还得夜里开流、耗电）。

**要你给**：读 `HuaweiState.getSupportsRriNewSync()` 的所有使用点，回答：

1. 这个能力位现在有代码真的在用吗？还是只是被记录？
2. `rri=true` 是「支持 RRI 新同步协议」还是「支持 RRI 实时流」？
3. 如果它意味着**RRI 也有文件通道**（像 sleep_data 一样按 id 取），
   那个 id 是哪个？`0x03 rri_data` / `0x04 once_rri` / `0x10 rrisqi` 我们都试过是 0 字节 ——
   是不是需要先用某个命令「结算」当天数据（比如 `0x2C/0x06 Complete` 或 `0x19/0x01 type=4`）？

这一条如果成立，收益最大：**不用整夜开流就能拿到逐拍数据**，耗电和时段限制都消失。
