## 2. 发现

严重度：**高** = 会丢数据或让下游得出错误结论；**中** = 行为与设置或文档不符；**低** = 维护性。

### 2.1 已在 `patches/0002-*.patch` 里修掉

| # | 严重度 | 位置 | 问题 | 修法 |
|---|---|---|---|---|
| 1 | 高 | `HuaweiSupportProvider.onFetchRecordedData` | `enqueueProbeDownloads()` 每次同步无条件运行。它用 0x2C 请求 17 个文件 id，其中有 `sleep_state.bin`、`sleep_data.bin`、`rrisqi_data.bin`，回调只打一行日志就把数据丢了，而且排在归档请求前面。`patches.md` 说研究脚手架「默认不参与运行」，README 说「同一个文件只允许一个消费者」，这段代码两条都违反，`patches.md` 的脚手架表里也没有列它 | `RESEARCH_FILE_PROBES = false` |
| 2 | 高 | `DatabaseExportWorker.doWork` | 某张表导出抛异常、或 manifest 写失败，增量游标照样推进。下一轮只回看 1 小时，这张表更早的行不会再出现在任何 CSV 里 | 整批成功才推进游标；失败的表记进 `failed_tables` |
| 3 | 高 | `DatabaseExportWorker.pruneOld` | 只保留最新 7 个 manifest，CSV 从不清理。导出间隔是几小时时，下游停一天就有批次的 manifest 被删（CSV 还在但没人认领），同时 CSV 无限增长 | 按文件名时间戳保留 14 天，manifest 和 CSV 同一条规则 |
| 4 | 高 | `DatabaseExportWorker.writeManifest` 的 `unique_keys` | 手写的去重键是错的。活动表真实主键是 `(TIMESTAMP, DEVICE_ID, OTHER_TIMESTAMP, SOURCE)`，manifest 给的是 `(TIMESTAMP, OTHER_TIMESTAMP)`；`workout-summary`、`workout-pace`、`device-attributes` 没有条目；`TableSpec.uniqueKey` 字段从没被用过，其中两个值也是错的 | 从 `PRAGMA table_info` 读主键，写进 `files[].primary_key` / `key_columns`，`unique_keys` 由它生成 |
| 5 | 高 | `decoders/analyse_rri.py` | `rows.sort()` 对 `(epoch_s, rri, sqi)` 整体排序。一包 14 拍共用一个 `epoch_s`，于是包内被按 RRI 从小到大重排，RMSSD 和 pNN50 都算错（合成数据上 56.2 → 40.1 ms，35.4% → 8.3%） | 只按时间戳稳定排序 |
| 6 | 中 | `ResponseManager.appendRriToFile` | TLV 长度只读 1 个字节。现在一包 14 条记录正好 126 字节，没出事；一旦设备发 15 条（135 字节，长度占 2 字节），整包被静默丢弃 | 按 VarInt 读长度 |
| 7 | 中 | 同上 | `sqi == 0` 的拍被丢掉。原始采集不应该做不可逆的过滤，丢拍还会打断逐拍序列 | 全部写入，`analyse_rri.py` 本来就自己过滤 `sqi > 0` |
| 8 | 中 | `GBApplication.onCreate` | `PeriodicSyncScheduler.start()` 在 `prefs` 赋值之前调用。`getPrefs()` 返回 null，空指针被 `intervalMs()` 的 catch 吞掉，结果每次进程启动都按默认 6 小时排，设成「关闭」或 24 小时都不生效，直到用户再改一次设置 | 挪到 `prefs` 初始化之后 |
| 9 | 中 | 同上 | 偏好监听器是没有强引用的 lambda。`SharedPreferences` 用 `WeakHashMap` 存监听器，GC 之后改设置不再重排闹钟 | 存进静态字段 |
| 10 | 中 | `DatabaseExportWorker.exportDelta` / `writeManifest` | 每个文件各调一次 `stamp()`。导出跨过整秒时，同一批文件会带两个时间戳，契约里「同一次导出共享一个时间戳」不成立 | 一次导出只取一个 `batch` |
| 11 | 中 | `DatabaseExportWorker.writeManifest` | manifest 直接写最终文件名，下游可能读到写了一半的 JSON | 先写 `.json.tmp` 再改名，改名失败退回原做法 |
| 12 | 中 | `DatabaseExportWorker.copyRawBlobs` | 先对文件算 sha256，再重新打开文件拷贝。RRI 文件整夜在追加，两次读之间多了几行，索引里的哈希就和归档出去的字节对不上 | 文件只读一次，哈希和写出用同一份字节；manifest 新增 `raw_archive`（name / bytes / sha256 / changed / complete） |
| 13 | 中 | `HuaweiSupportProvider.enqueueFullSleepDump` | 每次同步在 `files/dump/` 存一份约 100 KB，永不清理；`fr.getData()` 为 null 时在 try 外抛空指针；0 字节也会存 | 空的不存、相同的不存、只留最新 5 份 |
| 14 | 中 | `HuaweiSupportProvider` 忙碌看门狗 | 累计的是「采样时处于 busy 的分钟数」，不管是不是同一个任务，连续几个正常任务也会被当成卡死；`dispose()` 不停它，每次重连多一个空转的定时器 | 任务名变了就清零；`dispose()` 里移除 |
| 15 | 低 | `data_quality` | 活动表成对行使 `interval_median_s` 恒为 0、`gap_count_gt_2x_median` 没有意义 | 时间戳变化才算一个间隔 |
| 16 | 低 | `onFetchRecordedData` | 打印 `DEBUG_FILELIST requested`，但请求早就停用了，日志在说谎 | 删掉这行日志 |
| 17 | 低 | README / `upstream-baseline.md` | 让人 checkout `0.95.1`，但补丁在这个 tag 上套不上（`arrays.xml`、`strings.xml` 失败）；文档写「没有精确 commit」 | 写明基线提交 `6a322305` 和定位方法 |
| 18 | 低 | README | 导出目录结构还是旧的 `raw-sleep_data_<epoch_ms>.bin` | 更新 |
| 19 | 低 | `docs/pipeline.md` | 整篇是已经废弃的 adb 拉 `.db` 管线，引用的 `sync.py` 等不在仓库里，还写着「心率无」 | 文首加说明，标为历史文档 |
| 20 | 低 | 仓库根目录 | 公开仓库、内容是 AGPL-3.0 代码的衍生补丁，却没有 LICENSE 文件 | 加上 AGPL-3.0 全文 |

### 2.2 没有改，需要 PC 侧在真机上确认或由 Frank 决定

| # | 问题 | 为什么没改 | 建议 |
|---|---|---|---|
| A | **RRI 流到底会不会自己停。** [`protocol-findings.md`](protocol-findings.md) 8.1 写「设备约 20 秒后自行关闭流」，所以才有 15 秒一次的保活；[`patches.md`](patches.md) 又写「设备不会自己停流，到 08:00 必须主动关」。两句话只能有一句对 | 只有手表能回答 | 08:00 后看 `raw-rri` 是否还有新行。如果不发关闭命令、只停保活，流也在 20 秒内停，那 `closeRriStream()` 是多余的；反之保活间隔可以放宽 |
| B | **两个耗电数字对不上。** 白天开流 2.5%/小时，整夜 8 小时只掉 3% | 同上 | 用 `raw-capture` 时间线和 `raw-rri` 的行数核对夜里实际开流了多久 |
| C | **RRI 包之间有没有重复的拍。** 文档说约 4 秒一包、每包 14 拍；心率 60–100 时 4 秒只有 4–7 拍。要么包间隔其实更长，要么相邻的包有重叠。有重叠的话，现在所有 HRV 指标都把拍数算重了 | 没有真实文件 | 跑 `python decoders/check_rri_packets.py <raw-rri 文件>`（本次新增），结果是 `OK` / `OVERLAP` / `SUSPECT` |
| D | **「手表每个数据文件只发一次」是否成立。** 第 1 条说明：过去每次同步 `sleep_data.bin` 先被探针拿走一次，`FULLDUMP` 随后还能拿到 105716 字节（`nightly-check.ps1` 第 4 步一直在过）。这和 README「三条发现」的第 ③ 条矛盾 | 只有手表能回答 | 关掉探针后看 `FILEDL_INIT name=sleep_data` 是否仍然每次都有 size。如果有，把第 ③ 条改成它真正适用的范围（看起来只是 0x0A 探针） |
| E | **`sleep_data.bin` 每次同步仍然下载两遍。** `enqueueFullSleepDump()` 归档一遍，`downloadTruSleepData()` 给上游解析再下一遍，窗口都是 48 小时 | 合并成一次要改上游的回调，风险比收益大，而且要真机验证 | 可以在 `SleepFileDownloadCallback.syncComplete` 里顺手归档 `sleepData`，然后去掉同步路径上的 `enqueueFullSleepDump()`；先不动 |
| F | **忙碌看门狗在掩盖什么。** 它 10 分钟后强制清 busy，但不清 `HuaweiFileDownloadManager` 里卡住的当前请求 | 要看真机日志才知道是哪个请求不返回 | 关掉探针后观察 `BUSY_WATCHDOG clearing` 还出不出现。不出现的话，卡死的根因就是那 17 个探针请求 |
| G | **manifest 的 `user` 块带姓名、生日、性别、身高、体重**，文件在共享存储里 | 要不要这些字段是 Frank 的决定 | 建议去掉 `name` 和 `birthday_ms`；身高体重在 `user-attributes` CSV 里已经有历史 |
| H | **`HRRRI_RAW` 每包打一行完整十六进制**，一夜约 2 万行 INFO 日志，日志文件里因此有全量心跳数据 | 现在还在靠它排障 | 稳定后降到 DEBUG |
| I | **`PeriodicSyncReceiver` 先 `connect()` 再立刻 `onFetchRecordedData()`**。没连上时这次 fetch 会被直接丢掉，靠的是连接成功后那一次自动归档 | 改它要验证重连时序 | 断开状态下触发一次定时同步，确认日志里有没有完整的 `sync complete` |
| J | **`workout-pace` 没有时间列**，CSV 的 `epoch_s` 是导出时刻，不是数据时间 | 契约问题 | 在 mailuo 的契约文档里写明 |
| K | **8 个 `Send*Probe*.java`（约 1000 行）和 `ResponseManager` 里的探针日志仍在生产补丁里**，虽然入口都注释掉了 | 拆补丁会让这个 PR 无法评审 | 下一步把它们拆成单独的 `research-probes.patch`，生产补丁只留「生产必需」 |
| L | **`downloadStressData` 去掉了能力位判断**，于是每次同步都请求一次恒为 0 字节的 `rrisqi_data.bin` | 无害 | 可以恢复上游的判断 |

## 3. 合并前 PC 侧要做的事

按顺序做，每一步都有明确的通过条件。任何一步不过就停下，把日志贴到 PR 里。

1. **编译。** 新 clone 上游，`git checkout 6a322305eae857436e77b3a0f5b3ebc438b047e9`，`git apply patches/all-changes.patch`，`tools\build-gb.ps1`。
   通过条件：`BUILD SUCCESSFUL`。如果只在 3 个 Java 文件里报类型错误，把错误原文贴出来，不要自己猜着改。
2. **装机并连表**，然后跑 `tools\nightly-check.ps1`。通过条件：5 项全过，和改之前一样。
3. **确认探针已停。** 手动同步一次，在日志里搜 `FILEDL_DONE` 和 `FILEDL_FAIL`。通过条件：一行都没有。`FILEDL_INIT name=sleep_data` 每次同步不超过 2 行（归档一次、解析一次），不再是 3 行。
4. **确认导出是 schema 6。** 触发一次自动导出，打开最新的 `manifest-*.json`：
   - `schema` 是 6，有 `batch`，并且等于文件名里的时间戳；
   - 同一批所有 CSV 的时间戳都等于 `batch`；
   - `files[0].table` 是 `HUAWEI_ACTIVITY_SAMPLE`，`primary_key` 是 `["TIMESTAMP","DEVICE_ID","OTHER_TIMESTAMP","SOURCE"]`，`key_columns` 是 `["epoch_s","DEVICE_ID","OTHER_TIMESTAMP","SOURCE"]`。**如果 `primary_key` 是空数组或和这里不一样，说明这台机器上的表结构和我读到的不同，要回报**；
   - `raw_archive` 里每个文件的 `sha256` 和导出目录里实际文件的 sha256 一致（`Get-FileHash`）；
   - 目录里没有残留的 `.json.tmp`。
5. **注意第一次导出会清理旧文件。** 时间戳超过 14 天的 manifest 和 CSV 会被删掉（数据仍在 Gadgetbridge 的数据库和 `.db` 快照里）。想留就先把整个导出目录拷一份。
6. **回答 2.2 的 A、B、C、D、F**，把结论写回对应文档。C 直接跑脚本。
7. 把 mailuo 的契约文档升到 schema 6，并把真机的 schema 6 manifest 换上去（记得脱敏，脱敏表里不要写原值）。
