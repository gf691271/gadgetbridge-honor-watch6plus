## 1. 「停顿」不是没收到包，是**设备在发空包**

原来从 CSV 算出的「30% 时间在停顿里，最长 62 分钟」，是**错读**：CSV 只写 `rri > 0` 的拍，
所以空包在 CSV 里等于不存在。

日志里的真相：

| 项 | 值 |
|---|---|
| 整夜 `0x19/0x05` 帧 | **5,644** |
| 相邻两帧最大间隔 | **42 秒**（没有一次超过 60 秒） |
| 62 分钟「停顿」期间实际收到的帧 | **148 个** |
| 其中时间戳为 0（`01 04 00000000`） | 110 个 |
| 其中带真实拍的 | **1 个**（02:04:11，就是停顿前最后一个） |

空包长这样（同一帧里 14 个槽位全是 0）：

```
5A0092001905 0104 00000000 060100 070100 080100 827E
  8307 0402 0000 0501 00  8307 0402 0000 0501 00 ...
```

**结论：链路一直是活的，设备每 ≤42 秒送一帧，只是那段时间 PPG 没有脉搏可报。**
所以「覆盖率 0.77 / 0.80」的正确含义是「**那一晚约 20% 的时间传感器拿不到脉搏**」，
不是「我们丢了 20% 的拍」。

整夜统计：

| 分类 | 帧数 | 占比 |
|---|---|---|
| 带真实拍 | 5,056 | 89.6% |
| 全零（ts=0，无脉搏） | 352 | 6.2% |
| `0x1E84A` 错误应答 | 236 | 4.2% |

按小时看，**02:00 那一小时最差**（161 帧里 110 帧全零，68%），其余小时 2–12%。

**那个 `ts <= 0` 的过滤是对的**：352 个 ts=0 的帧里，带真实拍的是 **0 个**。
不存在「因为时间戳为 0 而丢掉真数据」。

## 2. 我们的「15 秒重发」被设备拒绝了 —— 82% 的错误帧是它引起的

`0x19/0x05` 上除了数据，还有 236 帧是纯错误码：

```
5A0009 0019 05 7F04 0001E84A      → 0x0001E84A = 125002
```

这个码在笔记里没有出现过（已知的是 `0x186A0` = 成功、`0x23281` = 类型有效但无数据）。

**关键相关性：194 / 236（82%）发生在我们发出开流请求后的 10 秒内。**

| 小时 | 错误帧 | 该小时总帧 | 占比 |
|---|---|---|---|
| 00 | 45 | 631 | 7% |
| 01 | 89 | 775 | 11% |
| **02** | **40** | **161** | **25%** |
| 03 | 27 | 777 | 3% |
| 04–07 | 35 | 3,294 | ~1% |

**推断：流已经开着时再发 `0x19/0x01 type=3`，设备回 `0x1E84A` 拒绝。**
也就是说我们整夜 1,304 次重发里，绝大多数是无效动作 —— 不改变采集状态，只是
多一次写 socket、多一次错误应答。

另一个细节：实际重发间隔是 **21 秒（中位）不是 15 秒**，因为
`rriRepeat` 把 `postDelayed(15000)` 排在 `openRriStream()` **之后**，而写 socket 是
`synchronized` 的（`BtClassicIoThread.write` → `mOutStream.write/flush`），会和读线程抢锁。
无信号时段更慢：**34 秒**（每次写要等更久）。

## 3. 看门狗（0005）不会误触发 —— 有 20 倍余量

- 整夜相邻 `0x19/0x05` 帧最大间隔 **42 秒**
- 0005 的阈值是 **900 秒**
- 因此「15 分钟没有任何 RRI 包」在这块表上几乎不可能自然发生

同时确认 `markRriPacket()` 对**空包也会调用**（它在 `ResponseManager` 里位于
`appendRriToFile` 之后、与 ts 无关），所以空包不会让看门狗误判。

11-15 夜里日志里没有 `RRI_LINKSTALE`（0005 是 16 日 09:00 才装的），这项要今晚才有数据。

## 9. amp 与 ACC 第 3 字节：实测结论（2026-11-16 12:30）

### 9.1 amp 是 RAW（`0xAA`），不是压缩流

真实布局（129 字节记录、count=40 为例）：

```
peak 流：BB + 初值(2) + (count-1) 字节        -> j = 47
amp  流：AA + count x 2 字节                  -> 47 + 1 + 80 = 128
尾部：1 个 0x00                               -> 129 ✓
```

所以上游走 **RAW 分支**（`read count shorts`），长度检查不会失败，不会丢记录。
我们的解码器也是 RAW + 小端，与上游一致。

「`40961, 0,0,0,0, 20169, 65535x4, ...`」这个规律**只出现在前 6 条热身记录**，
跳过前 6 条后稳态数据没有 0/65535 的交替，所以它不是解码错误。

大小端判不出来：peak 是 LE（C3 已验证），amp 用「相邻差/标准差」评分 LE 0.324、BE 0.324，
控件（peak）0.176。倾向 LE。

### 9.2 ACC 第 3 字节的结构

| 观察 | 值 |
|---|---|
| 相邻差 | 只有 ±64（+64 出现 140 次，-64 出现 123 次） |
| 高 2 位 | 严格 0,3,2,1 循环 |
| 低 6 位 | 每 4 条变一次（`4,4,4,5 \| 5,5,5,26 \| 26,26,26,27 \| ...`） |
| `(b3 + ts) mod 256` | 159 个不同值，**不是常数** |

是一个「2 位 mod-4 计数器 + 6 位慢变值」的字段，具体含义未解。

### 9.3 ACC 位图（采纳复核意见）

混合值都是连续一段 1，`0xFFFF` = 睡梦中不可能连续 91 分钟全动 → 是「没戴」哨兵。
**「三轴活动度 / 第 3 轴重力」的说法作废。**

## 10. TruSleep 的真模型：ON 录、OFF 读（6 份日志交叉验证）

翻 11-09 到 11-16 六份日志（含轮转 zip），列出每次 `0x07/0x16` 的实际发送值，与
`sleep_data.bin` 的 size 对齐：

| 日期 | TruSleep | sleep_data size |
|---|---|---|
| 11-09 | OFF | **78052**（18:27 出现） |
| 11-10 | OFF | 78052（同一份） |
| 11-11 | 08:20 前 OFF，**14:00 起 ON** | 14:00 还是 78052；**20:01 变 0** |
| 11-12 | **ON 全天** | **0（每一次）** |
| 11-13 | **10:45 切回 OFF** | 02:12 = 0；**10:47 出现新的 105716** |
| 11-14 | OFF | 105716（同一份） |
| 11-15 | OFF | 105716 到 14:08，然后 0 |
| 11-16 | OFF | 0 |

两个现场：

```
11-11 14:00  size=78052
11-11 14:00  === GB sends TRUSLEEP=ON ===
11-11 20:01  size=0          <- 拨 ON 后读不到

11-13 10:45  === GB sends TRUSLEEP=OFF ===
11-13 10:47  size=105716     <- 两分钟后新文件出现
```

**模型：**

| TruSleep | 夜里录制 | 早上能读 |
|---|---|---|
| OFF | ❌ 不录 | ✅ 能读已存在的那份 |
| ON | ✅ 录 | ❌ 返回 0 |

`pitfalls.md` A1 说「必须保持 false 否则读不到」只对了一半：**false 同时意味着不录**。
这正是 11-13 之后一直没有新 blob 的原因。

**生产流程（待 R2 验证）：** 夜里 ON 录音 → 早上第一次连接切 OFF 读文件 → 拨回 ON。

**今晚判读表的修正：** R1（ON 读）**一定是 0，这是模型的一部分，不是失败**；
R2（切 OFF 重连再读）才是判决步。

## 12. 复核第 15 条的六项（2026-11-17 下午）

### 12.1 单字节采样是有符号读的（已修，有生产数据为证）

`FitnessData.MessageData.StepResponse.parseData` 里两处 `data[i++]` 直接赋给 `short`/`byte`：
单字节标签（0x20、0x40=心率）与第二张位图（0x01=血氧、0x02=静息心率）。

库里的证据：

```
HEART_RATE n=28275  min=-127  max=125   值 < -1：4 行（-127/-124/-116/-109 = 129/132/140/147 bpm）
SPO / RESTING_HEART_RATE / STEPS   值 < -1：0 行
128 以上一个都没有 —— 全被翻成负数
```

**步数不受影响**（两字节路径两个字节都 mask 了）。
两处都加了 `& 0xFF`；新增 `TestFitnessDataSignHandling`，4 个用例全过。

### 12.2 分期行是事件，而且有两个生产者

- 每个段写**两行**（`start→end` 与 `end→start`），镜像行的 `end - start` 是负数。
  消费端必须只取 `OTHER_TIMESTAMP > TIMESTAMP`。
- **`0x0D`**（`GetSleepDataRequest`）= 细粒度分期，含 **kind 7 深睡**
- **`0x0A`**（`sleep_state.bin`）= **只有 kind 6**

| 夜 | TruSleep | kind 6 来源 | kind 7 | kind 8 |
|---|---|---|---|---|
| 11-14→15 | OFF | 全 0x0D | 15 | 4 |
| 11-15→16 | OFF | 全 0x0D | 16 | 4 |
| **11-16→17** | **ON** | **0x0A** | **0** | 14（全 1 分钟） |

**TruSleep=ON 的夜晚深睡完全消失，REM 退化成 1 分钟碎片，
剩一个 290 分钟的「浅睡」大块（02:13→07:03）。** 这是开 TruSleep 的代价。

### 12.3 上午重试（已实现，未真机验证）

## 14. L3 答案：TruSleep=ON 那夜 `0x0D` 报了 7 个 1 分钟的 type 8，没有 6 也没有 7

`SOURCE=0x0D` 在 11-16 20:00 → 11-17 12:00 的窗口里共 76 行 = **38 个逻辑段**，
类型分布 **`{1: 30, 3: 1, 8: 7}`** —— 30 个活动段证明 `0x0D` 那晚确实跑了，
但它**没有产生任何浅睡 6 或深睡 7**，只有 7 个 1 分钟的 type 8：
23:34、00:00、02:15、07:03、08:00、08:30、08:52。

所以「深睡消失」不是「请求没发」，而是**报的内容变了**。

**观察（推断，只有一夜）**：7 个 type 8 里有 5 个落在同夜 `0x0A`（`sleep_state`）分段的
边界或空隙上（07:03、08:00、08:30 正好是段结束；23:34、00:00 落在空隙）。
如果成立，type 8 更像**状态切换标记**而不是有时长的分期段。**不当结论。**

### 14.1 L3 收尾：TruSleep=ON 会让设备换成「粗粒度」上报（9 夜 9/9）

按夜统计 `RAW_KIND` 的来源分布：

| 夜（早晨） | 0x0A k6 | **0x0D k6** | **k7** | k8 | 模式 |
|---|---|---|---|---|---|
| 11-08 | 6 | 0 | **0** | 6 | B |
| 11-09 | 12 | 0 | **0** | 12 | B |
| **11-10** | 0 | **16** | **14** | 2 | A |
| **11-11** | 0 | **12** | **10** | 2 | A |
| 11-12 | 2 | 0 | **0** | 2 | B |
| 11-13 | 2 | 0 | **0** | 2 | B |
| **11-15** | 0 | **20** | **15** | 4 | A |
| **11-16** | 4 | **20** | **16** | 6 | A |
| **11-17** | 14 | **0** | **0** | 14 | B |

**规律：`0x0D` 产 k6 的夜一定同时产 k7；不产 k6 的夜 k7 一定为 0，只剩 1 分钟的 k8。**

与 TruSleep 实际下发值对照：ON 的夜（11-12、11-13、11-17）全是模式 B；
OFF 的夜（11-10、11-11、11-15、11-16）全是模式 A。
11-08/11-09 是手表默认状态，也是 B —— 说明**模式 A 需要显式发 OFF 才出现**。

**所以 L3 不是「设备不发」也不是「解析丢了」，而是开关让设备换了上报路径。**
「无法判断」的部分收窄到「原始 0x0D 报文没有落日志」，要升到已验证需改代码存原始包。

**代价清单**（重要）：开 TruSleep 拿到原始逐拍 blob，但**失去深睡分期**；
阶段 1 实验期间 TruSleep 保持 ON，所以这几天的分期数据都不含深睡，分析侧要知道。

### 14.2 主键构成：跨来源不会互相覆盖

```sql
PRIMARY KEY ("TIMESTAMP", "DEVICE_ID", "OTHER_TIMESTAMP", "SOURCE") ON CONFLICT REPLACE
```
`insertOrReplaceInTx` 写入。**`SOURCE` 在主键里**，所以 `0x0A` 与 `0x0D` 的行永不冲突，
「0x0A 覆盖了 0x0D 的深睡」在结构上排除；同来源覆盖要求 `(起, 止)` 完全一致。
