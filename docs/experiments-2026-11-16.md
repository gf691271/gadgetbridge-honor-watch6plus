# 11-16 夜：三个问题的真答案（都不是我们原来以为的那个）

数据：`gadgetbridge.log`（00:00–10:07）+ `rri_20261116.csv`（00:14:18–08:00:20，5,058 包）。
工具：`decoders/check_open_requests.py`（本轮新增）。

## 1. 「停顿」不是没收到包，是**设备在发空包**

原来从 CSV 算出的「30% 时间在停顿里，最长 62 分钟」，是**错读**：CSV 只写 `rri > 0` 的拍，
所以空包在 CSV 里等于不存在。

日志里的真相：

| 项 | 值 |
|---|---|
| 整夜 `0x19/0x05` 帧 | **5,644** |
| 相邻两帧最大间隔 | **42 秒**（没有一次超过 60 秒） |
| 62 分钟「停顿」期间实际收到的帧 | **148 个** |
| 其中时间戳为 0（`01 04 00000000`） | 110 个 |
| 其中带真实拍的 | **1 个**（02:04:11，就是停顿前最后一个） |

空包长这样（同一帧里 14 个槽位全是 0）：

```
5A0092001905 0104 00000000 060100 070100 080100 827E
  8307 0402 0000 0501 00  8307 0402 0000 0501 00 ...
```

**结论：链路一直是活的，设备每 ≤42 秒送一帧，只是那段时间 PPG 没有脉搏可报。**
所以「覆盖率 0.77 / 0.80」的正确含义是「**那一晚约 20% 的时间传感器拿不到脉搏**」，
不是「我们丢了 20% 的拍」。

整夜统计：

| 分类 | 帧数 | 占比 |
|---|---|---|
| 带真实拍 | 5,056 | 89.6% |
| 全零（ts=0，无脉搏） | 352 | 6.2% |
| `0x1E84A` 错误应答 | 236 | 4.2% |

按小时看，**02:00 那一小时最差**（161 帧里 110 帧全零，68%），其余小时 2–12%。

**那个 `ts <= 0` 的过滤是对的**：352 个 ts=0 的帧里，带真实拍的是 **0 个**。
不存在「因为时间戳为 0 而丢掉真数据」。

## 2. 我们的「15 秒重发」被设备拒绝了 —— 82% 的错误帧是它引起的

`0x19/0x05` 上除了数据，还有 236 帧是纯错误码：

```
5A0009 0019 05 7F04 0001E84A      → 0x0001E84A = 125002
```

这个码在笔记里没有出现过（已知的是 `0x186A0` = 成功、`0x23281` = 类型有效但无数据）。

**关键相关性：194 / 236（82%）发生在我们发出开流请求后的 10 秒内。**

| 小时 | 错误帧 | 该小时总帧 | 占比 |
|---|---|---|---|
| 00 | 45 | 631 | 7% |
| 01 | 89 | 775 | 11% |
| **02** | **40** | **161** | **25%** |
| 03 | 27 | 777 | 3% |
| 04–07 | 35 | 3,294 | ~1% |

**推断：流已经开着时再发 `0x19/0x01 type=3`，设备回 `0x1E84A` 拒绝。**
也就是说我们整夜 1,304 次重发里，绝大多数是无效动作 —— 不改变采集状态，只是
多一次写 socket、多一次错误应答。

另一个细节：实际重发间隔是 **21 秒（中位）不是 15 秒**，因为
`rriRepeat` 把 `postDelayed(15000)` 排在 `openRriStream()` **之后**，而写 socket 是
`synchronized` 的（`BtClassicIoThread.write` → `mOutStream.write/flush`），会和读线程抢锁。
无信号时段更慢：**34 秒**（每次写要等更久）。

## 3. 看门狗（0005）不会误触发 —— 有 20 倍余量

- 整夜相邻 `0x19/0x05` 帧最大间隔 **42 秒**
- 0005 的阈值是 **900 秒**
- 因此「15 分钟没有任何 RRI 包」在这块表上几乎不可能自然发生

同时确认 `markRriPacket()` 对**空包也会调用**（它在 `ResponseManager` 里位于
`appendRriToFile` 之后、与 ts 无关），所以空包不会让看门狗误判。

11-15 夜里日志里没有 `RRI_LINKSTALE`（0005 是 16 日 09:00 才装的），这项要今晚才有数据。

（`origWhen=10:16:27 window=+11m15s`）。

**顺带纠正 11-15 的根因**：那天 22:02 我 `am start` 之后 GB **连「尝试连接」都没记**
（`22:01:45 Previous process exit` 之后到 22:10 无任何连接日志）。今天验证了原因：
**只有界面真的 resume 时才会连**。今早 09:59 我 `am start` 时屏幕亮着 → 立刻连上；
10:01 把屏幕关掉再 `am start` → 没有连接。所以 11-15 那晚是「屏幕黑着 + autoconnect=false」
两个条件同时成立，谁都没去连。

## 6. 下一步（按证据排序）

1. **把重发改成「只在真的没包时才发」**：因为相邻帧最大间隔 42 秒，
   阈值取 **90 秒无任何帧** 才重发。预期收益：省掉 ~1,300 次无效写 + ~200 次错误应答。
   风险：如果 90 秒的重发太快导致设备拒绝，再放宽到 180 秒。
2. **不要用「没有拍」判断断流**（空包是正常状态），一律用「没有帧」。
3. **窗口时长**：省电只能靠缩短窗口。5 小时 = ~13.5%，4 小时 = ~11%。
4. 那个 **62 分钟的零信号段**（02:04–03:06）值得单独看：是不是离腕。
   可以拿 ACC（体动）三段数据比对 —— 如果同时段体动也全 0，基本就是离腕。
